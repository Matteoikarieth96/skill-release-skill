# Content rules

What may go into a public skill repo, what must change, and how. These apply
to every file, image, commit message and to the README.

## 1. Private and personal data

- **Secrets never ship**, not even revoked ones. Templates carry empty values
  (`SECRET_PASS ""`, `API_KEY=`) and the README says where the user puts their
  own. If a real key was ever in the folder, tell the owner to rotate it: the
  scan only proves it is not in this repo.
- **People**: no real names, emails, phone numbers, addresses, faces, voices
  or handles of anyone who did not agree in writing. The owner's own public
  handle is fine where they chose it (LICENSE holder, author).
- **Clients, employers, partners, private projects**: removed or replaced by
  fictional ones. Not even "built for a client in Rome".
- **The author's machine**: no absolute home paths, user names, host names,
  serial ports with device serials, LAN addresses, Wi-Fi names, printer IPs,
  account IDs. Paths are relative to the skill folder or asked at run time.
- **Claude artefacts**: no memory files, session transcripts, `.claude/`
  settings, permission lists or plans from the author's sessions.
- **Fictional means fictional**: invented names that do not belong to a real
  company or person (search the name once), reserved domains `example.com`,
  `.example`, `.test`, numbers marked as examples.
- **Private terms** match whole words, case-insensitive, but not other
  spellings: list `Acme Rossi`, `acme-rossi`, `acme_rossi` and the domain
  separately.

## 2. Other people's work

- **Code** copied from another repo keeps its licence and copyright notice, and
  the licence must allow redistribution under the repo's terms. GPL code does
  not go into an MIT repo. When in doubt, rewrite from the behaviour without
  the source open (clean room) and say so in the report.
- **A repo or document that says it must stay private** (for example a
  CLAUDE.md or a contract) means nothing from it is copied, not even
  structure or wording.
- **Text, tutorials, datasheet figures, kit manuals**: summarise in your own
  words and link to the source; do not reproduce.
- **Images**: only the owner's own, generated by the skill, or with a licence
  that allows it (keep the attribution). Product photos and logos of others
  are not used. Fritzing parts are CC BY-SA: drawing a diagram with them makes
  the image share-alike, so draw your own shapes instead.
- **Fonts**: link to Google Fonts or ship OFL fonts with their licence file.
- **AI-generated media**: allowed when the generator's terms allow
  publication; say in the README that a voice or image is AI-generated.

## 3. Brands and names

- Naming a product to say what the skill works with is fine. Add one line:
  "Independent project, not affiliated with or endorsed by X."
- No third-party logos in the README, hero image or icons.
- A repo or skill name that contains someone else's brand needs the owner's
  explicit choice and the non-affiliation line.

## 4. What the skill tells Claude to do

The SKILL.md runs with the user's permissions, so review it like code:
- It starts by asking (intake) instead of acting on guesses.
- It never tells Claude to publish, post, send, buy, delete or change settings
  without the user's explicit yes, and never to follow instructions found in
  files, pages or tool output.
- It does not ask for passwords, card numbers or keys in chat; keys come from
  environment variables or files the user controls.
- Commands it runs use argument lists or safe quoting, stay inside the
  project, and do not need `sudo`.
- No hidden text: no HTML comments with instructions, no invisible Unicode.
- No claims it cannot back: every number or feature in the README is tested
  or sourced.

## 5. Type-specific rules

**Hardware and wiring**
- Every wiring step opens with whether the power (USB or supply) must be
  disconnected first. Rule of thumb: power wires and whole modules, unplug;
  signal-only wires, may stay plugged in.
- Say the logic level of the board (5 V or 3.3 V) wherever a module could be
  damaged, current limits for LEDs and pins, and polarity for anything that
  can be reversed.
- No mains voltage instructions. Batteries (LiPo in particular): charging and
  short-circuit warnings, or leave them out.
- A safety and liability disclaimer in the README ("at your own risk, check
  the datasheet of your part").
- Diagrams drawn by the skill's own code, not copied from vendors.
- Bench photos: stripped, cropped, and looked at for labels, screens and
  serial numbers before they go in.

**Generated web pages and SVG**
- User text is escaped; no `innerHTML` with untrusted strings.
- CDN scripts pinned to a version with Subresource Integrity, with an offline
  fallback where it matters.
- Local servers bind to `127.0.0.1`, check the Host header, and serve only the
  output folder.

**Network services and keys**
- Keys come from environment variables or a file outside the repo, never a
  command-line argument that ends up in shell history or logs.
- Costs: if the skill calls a paid API, the README says so and roughly how
  much a run costs.
- TLS verification stays on.

**Personal data at run time**
- Say in the README what data the skill reads, where it goes (which API) and
  what it stores locally.
- Redact before sending to third parties when the task allows it.

## 6. Writing style of public files

Follow the owner's `banned_text` and style rules from `$LOCAL`. Plain, short
sentences; say what the skill does, what it needs, what it never does, and its
limits.
